# 研究目的、成功标准与算法迭代指南

版本：2026-09-23 / v2。供另一设备的研究与代码助手先读，再读 IMPLEMENTATION.md 和 experiment_spec.json。

## 1. 这项实验究竟要回答什么

本项目研究的是 MCSD 与 MCSD-TP 的统一约束优化框架。第三组语言模型实验的任务，是检验该框架能否在真实随机训练、混合精度和有限计算预算下，产生有竞争力、可解释且可复现的结果。

我们希望得到三类证据：

1. **覆盖范围：** 一套共同的更新逻辑，通过明确的几何接口，能处理 Frobenius 球面、spectral sphere 的光滑区域及 scaled Stiefel。框架覆盖不等于三种几何具有相同的表现，也不等于谱球面的全部非光滑位置都已被纯 MCSD 覆盖。
2. **算法价值：** 在同一约束、同一网络、同一数据预算、公平调参下，MCSD/MCSD-TP 相对强基线在验证质量、稳定性或实际计算成本上是否有价值；价值可能是折中，而不必是所有指标同时第一。
3. **机制与改进：** 当算法有效或失效时，能否通过对照将原因定位到切投影、有效步长、动量、LMO 精度或返回操作，并据此提出经检验的改进。

**不是预先承诺“MCSD 必须胜过所有基线”，也不能以这种目标挑选结果。** 没有优势、仅在部分几何有效、或谱球面光滑路线成本过高，都是需要保留并解释的研究结果。会议认可度取决于证据、问题价值与结论边界，不能由模型名称或一张胜出表保证。

## 2. 与整篇论文的关系

| 实验 | 主要承担的证据 | 不应承担的结论 |
|---|---|---|
| 第一组：传统随机 PCA / Stiefel 问题 | 目标误差、驻点指标、动量与 LMO 误差机制；便宜、可解释的数值检查 | 不能仅凭 PCA 优势推断语言模型更好 |
| 第二组：尚待选择的真实约束任务 | 补足应用或真正非光滑闭集 MCSD-PGD 的证据，按论文最终主张确定 | 目前未选定，不能写成已完成或已覆盖 |
| 第三组：本交接的固定架构语言模型 | 三几何接口的实际适用性、同约束内竞争力、质量与时间折中 | 不能凭 LM loss 曲线验证理论收敛速率，不能将跨约束排名当作同一问题上的算法优劣 |

Frobenius 球面和 Stiefel 本身是光滑流形。本包的纯 spectral MCSD 路线在已知奇异点停止，因而这组实验**尚不能替代 MCSD-PGD 的完整非光滑应用验证**。若后续引入混合/切换方法，必须另列更新规则、触发条件、理论适用性和实验名称。

main1.tex 只读。论文若需要新增假设、经验变体或更窄的适用范围，写到单独的 research/theory_alignment.md，供作者判断，不直接改正文。

## 3. 为什么固定小 Dense，哪些内容必须固定

选择现有 Megatron 中拟定的约 127M Qwen3-style Dense，是为利用已经跑通的训练系统和数据，把一个月的 8 张 H20 用于配对对照、多个种子与机制分析。它是本研究的小配置，不是声称复现某个官方 127M checkpoint。

主预算约 3B tokens 是**固定预算优化比较**，不能预先称作“充分训练”或“收敛完成”。从验证曲线尾部、延长预算及强基线的变化判断预算敏感性。如果 3B 排名在 6B 反转，应报告预算依赖，而不是只展示有利阶段。

主实验锁定：

- 网络层数、宽度、GQA、归一化、激活、tokenizer、数据 mixture 与顺序；
- 受约束的逻辑矩阵、组件分块规则、辅助参数处理；
- 同约束内初始权重、训练 tokens、评价切分、种子与 checkpoint 选择规则；
- 计算精度与计时规则，准确版和近似版分开命名。

每个方法的 LR 可以不同，且应各自公平调优。“所有算法用相同 LR”不等于公平。

跨约束初始化由同一个原始随机矩阵生成，但 Stiefel 必须改变其奇异值，所以不保证权重或函数完全相同。主方案匹配初始 Frobenius 能量；它并未同时匹配全部几何的算子范数或表达能力。报告初始验证 loss 与尺度。半径策略若改变，应成为单独的几何/尺度消融，不能替换不利的主结果。

## 4. 需要检验的假设及反例

以下是待检验的假设，而不是要求助手“证明正确”的既定结论。

| ID | 科学问题 / 待检验假设 | 最小有效对照 | 支持与不支持时如何解释 |
|---|---|---|---|
| H1 | 统一几何接口能正确实现三类约束下的更新 | 准确几何参考、完整 step、FP32 master、恢复一致性；谱路线记录退出边界 | 准确实现可运行支持实现覆盖；奇异点退出或成本过高应限定适用性 |
| H2 | 同约束内 MCSD/TP 相对强基线有质量或成本优势 | F 对 MuonH；St 对 iMuon 明确适配；S 对已有 SSO 与历史较强 MuonSphere | 只对被比较的几何、预算与基线作结论；不胜出时查机制，不能省略强基线 |
| H3 | 前置/后置切投影的作用不仅来自不同有效步长 | 共同 EMA、共同 LMO/返回的受控消融；F 做实际角度匹配 | 若匹配角度后优势消失，主要证据是步长机制；不能称为独立几何优势 |
| H4 | 实用 LMO/返回可在可接受误差下减少成本 | 固定 checkpoint 的准确-近似方向对照，随后短训练及独立正式确认 | 只变快但破坏可行性，不算原算法的成功加速；准确 LMO 的理论不能自动覆盖近似返回 |
| H5 | 有用的改善在独立种子与稍长预算中仍存在 | 开发与正式种子分开；预先选定的关键方法做 6B 完整调度 | 只在开发种子或单个阶段出现，应降级为探索性观察 |
| H6 | 谱球面不利结果可能来自几何边界、成本或步长，而非框架整体无效 | gap、投影类型、方向误差、计时分解、旧 MuonSphere 参照 | 光滑区退出只否定该路线在此设置中的可持续性；不等同全部 MCSD 或 MCSD-PGD 被否定 |

必要时保留 H2 的中性结果，只以 H1、机制证据和明确的质量—成本折中支撑论文。不能把“统一实现”本身包装成未经实验支持的性能优势。

## 5. 目标与验收：区分工程通过和研究成立

### 5.1 工程目标

- 实现公式对应当前论文，参考几何和完整训练 step 均有检查。
- 约束误差、矩阵分块、辅助参数路由和 checkpoint 恢复符合 IMPLEMENTATION.md。
- 每个 run 能追溯配置、代码、初始化、数据、近似精度和成本。
- 8 张 H20 的整月矩阵先按实测成本估算；计划不超过 4000 GPU-hours，另留 1760 作为余量。
- 三种几何均得到可运行证据或明确的未通过原因，不要求已知不适用配置强行完成长训。

这些通过，只说明实验系统可信，不说明算法优于基线。

### 5.2 科研评价的主次顺序

**主指标：** 同约束、相同约 3B 训练 tokens 下，最后 checkpoint 的独立 held-out NLL（越低越好）；报告 PPL、各正式种子的原值和配对差值。

**共同主视角：** NLL 对实际训练时间 / GPU-hours。若 tokens 指标更好而耗时显著增加，结论是质量—成本折中，不能直接称为加速。若仅在准确小实验运行过，则不声称在 H20 大规模训练更快。

**解释指标：** 稳定完成率、学习率容忍区间、约束误差、有效更新角度、切向/法向成分、LMO 误差、谱 gap 与返回开销。这些帮助说明原因，不能替代最终质量指标。

设每个正式种子上的差值为 Δ=NLL(候选)-NLL(同约束基线)，负值更好。报告三个配对差值、均值和离散程度；只有三个种子时不要把窄统计区间或单个胜出种子当作强普遍性证据。

在开发阶段、正式结果揭示前，登记“有实际价值的最小 NLL 改善量”和“值得采用的最小速度收益/可接受质量损失”。可以以 0.01 nats/token 和 10% 速度收益作为讨论起点，但**它们不是领域标准，也不是自动生效的阈值**。应结合开发波动、测量噪声与成本填写 acceptance_targets.json，留有理由。不能看完正式结果再移动门槛。

若声称 time-to-target 加速，先依据开发集确定固定目标 NLL，使用相同评估频率和插值规则；未达到者标记为未达到，不删除。

## 6. 最小机制实验：避免把所有差别算给 TP

### 6.1 Frobenius 球面优先做四个方向组合

在同一权重 W、当前 EMA M、谱 LMO、层尺度和同一径向返回下，开发对照：

| 前置切投影 | 后置切投影 | 作用 |
|---|---|---|
| 关 | 关 | 控制组：直接对 ambient M 做 LMO |
| 开 | 关 | MCSD |
| 关 | 开 | 单独检查后置切投影 |
| 开 | 开 | MCSD-TP |

控制组不能自动叫作原生 MuonH，因为 MuonH 的方向归一化、步长和动量可能不同。原生强基线竞争与共同组件消融是两套实验，分别标注。

先在相同 checkpoint、相同 M、相同 minibatch 上做单步诊断，避免轨迹不同导致无法解释方向差异；再在独立的完整短训练中检验累计效果。诊断用梯度不得改变正式运行的动量、随机流或数据进度。

F 球面的单步恒等式见 IMPLEMENTATION.md §4.1。在分母为正的适用条件下，记录 α_eff=α/(1+αb)，并加入实际角度匹配对照。匹配只依赖更新几何，不准用测试 loss 反向挑步长。角度匹配属于分析变体，要另有 method_id。

### 6.2 Stiefel 不要强造 MCSD/TP 差异

在正方块上，两方法可能在准确运算下重合。分别记录 Q/O 方阵与 K/V、MLP 矩形块的法向比例、更新距离和误差，检查差异是否来自矩形块或数值近似。

若两条更新实际一致，展示等价检查和适用条件即可；不通过改变精度、半径或不同动量来人为制造算法差距。

### 6.3 Spectral 主对比同时改变返回，必须拆开解释

本包的 MCSD 使用 exact metric projection，而 MCSD-TP 使用 radial retraction。二者的 loss 差异不能全部归因给“多了一次切投影”。

在光滑区域且小步长条件下，可做只用于机制研究的控制：

- 两个方向都使用 exact metric projection，在其确实是光滑局部投影的范围内比较前后切投影；
- 另将同一个 tangent 方向分别送入 exact projection 与 radial retraction，观察返回本身的影响；
- ambient 方向加 radial return 若测试，必须标为经验对照，不称为 exact MCSD。

每次控制先检查返回后的 gap。触及 tie 时停止该 pure-smooth 对照并报告；不能为了补齐曲线掩盖奇异点。

## 7. 测试结果如何转化成算法改进

按“观察 → 排除实现问题 → 提出单一假设 → 最小对照 → 独立验证”的顺序。不要同时改变动量、LR、半径、返回和数据。

| 观察 | 先查什么 | 合理的下一步 | 结论边界 |
|---|---|---|---|
| 前几步不动、方向为零或异常大 | g=None、零梯度、QKV 映射、当前 EMA、步长重复应用、主权重同步 | 修复与原定义不符的实现，重跑受影响测试和开发配置 | 这是 bug 修复，不是新算法；旧错误结果不可继续当基线 |
| MCSD/TP 在 F 上 loss 不同，但方向接近 | 法向比例、实际角度、α_eff、LR 范围是否覆盖 | 先扩展公平 LR 探索，再做角度匹配对照 | 若差距消失，优先解释为有效步长 |
| TP 明显更稳但较慢 | 后置投影是否重复计算，矩形块是否主导收益 | 缓存/批处理几何计算；另测显式 angle-control 变体 | 工程等价加速与改变步长算法要分开 |
| 准确版本正常、NS 版本发散 | LMO 范数可行性、线性误差、dtype、奇异值谱、返回误差 | 单独比较 FP32、迭代数或更准确 polar；每次只改一类误差源 | LMO 误差与返回误差不能混称为 inexact LMO |
| momentum 大时振荡或对 LR 很敏感 | EMA 系数方向、裁剪比例、动量切/法向分量 | 做 beta 对照；有证据后再试 transport 或切向动量变体 | transport/Nesterov 改变递推，当前 ambient-EMA 理论不自动适用 |
| spectral exact 很快进入 top tie | 是否是 clipping 的真实结果、初始化 gap、trial 谱 | 保留失败证据；研究较小步长、另一合法局部返回，或单独的混合 MCSD-PGD | 不把真实几何现象修成“容差问题”，不静默切换 |
| spectral 训练慢 | 反向、LMO、返回、gap 审计的时间占比 | 先复用已有 SVD，减少重复分解；近似 gap 路线另标经验版本 | 降低审计频率不能声称仍有逐步安全证书 |
| Stiefel 正确但质量较差 | 初始 loss、矩形方向、a 的尺度、辅助参数、表达限制 | 先同约束比较；必要时对所有算法共享地做半径/约束层选择消融 | 放松约束是在换模型问题，不是直接证明优化器改善 |
| 所有新算法都输给基线 | 基线身份、调参公平性、LR 边界、数据是否重复、实现误差 | 正确性通过后接受结果；选择有诊断依据的一个改进，不盲扫变体 | 不更换数据或移除强基线以制造胜出 |
| 3B 优势在 6B 消失 | 调度、预算迁移、末期学习率、验证趋势 | 相同完整调度和公平调参下复核关键方法 | 报告短预算优势，不能写成长预算普遍优势 |

候选算法改进按优先级考虑：

1. **先做数学等价的工程优化：** 重用几何量、避免重复 SVD、合并小矩阵处理、准确的内核实现。等价性和数值检查通过后测实际速度。
2. **再做原定义内的配置选择：** LR、beta、公平候选范围、理论允许的 LMO 误差配置。保持正式配置和开发配置分离。
3. **有证据再做结构变体：** 角度控制、transport、动量投影、适应性精度、其他返回或 MCSD-PGD 切换。新名字、新配置、写明假设变化，保留原 MCSD/TP 作为对照。

已有数学定义不因变体效果好而自动改变。是否纳入论文主算法，由作者结合理论与独立证据决定；部署助手可以实现、检验并提出建议。

改变网络、数据、受约束块、初始化策略、半径策略或公共辅助优化器，属于实验协议变更。需要新 protocol_id，并为受影响的比较方法建立共同条件；不能把协议变更后的新方法结果直接混入旧主表。

## 8. 给另一设备助手的迭代权限与工作方式

用户希望助手主动参与算法诊断和改进。不要只把“跑通”当作完成，也不要未经证据就全面改写算法。

### 可以直接推进的开发工作

- 修复违反冻结公式的实现问题，并说明修复影响。
- 做保持数学定义的性能优化，验证误差与输出一致性。
- 根据已有证据提出并实现单因素变体，保留原版；完成本轮已授权的测试和短运行。
- 维护研究记录，给出下一阶段的具体配置、成本及应回答的问题。
- 在不可运行的环境完成可做的本地部分，清楚区分未验证、失败与不适用。

本交接默认执行范围仍为实现、数值/集成测试和每个方法或已登记变体至多 100 个训练步；launcher 默认 dry-run。100 步只能判断接入、明显失稳和初步成本，**不能用于选择论文最终赢家**。较长 pilot、1B 搜索、3B/6B 正式作业按目标设备后续明确的执行预算推进；如果该会话已经授权相应阶段，无需重复索取许可。

每轮最多提出两个有证据的结构改进候选，避免候选数无界膨胀。候选的测试成本也计入开发总预算；共同强基线保留同等的可调参数探索机会。结构探索的总成本单列报告，而不是声称整个研究只花了主表的 GPU-hours。

### 每次结构变体必须登记

~~~text
variant_id:
parent_method_and_commit:
observation_and_run_ids:
hypothesis:
exact_change_in_equation_or_order:
what_stays_fixed:
theory_status: unchanged / needs_new_argument / empirical_only
affected_geometry_and_blocks:
minimal_control:
development_budget:
success_and_rejection_criteria:
result_and_uncertainty:
decision: keep / reject / needs_more_evidence
next_experiment:
~~~

写入 research/algorithm_decisions.md，并将配置放在独立变体目录。不能覆盖原方法的 config、run_id 或结果。

### 推进/停止规则

- **正确性未通过：** 优先修复，不做性能结论；允许保留不受影响的开发工作。
- **正确性通过但失稳：** 用短预算和单因素对照定位，暂不投入正式长训。
- **正确性和稳定性通过：** 根据实测成本与验证集趋势推进开发；不以 100 步训练 loss 判定优劣。
- **新变体在开发中有明确收益：** 冻结定义，进入独立种子和公平基线比较；收益不足或代价不值得则保留负结果，停止扩展。
- **已开始正式评估：** 不再依据最终测试结果回头调方法。若确有新研究周期，版本升级，并保留一个未用于选择的最终评估集。

## 9. 每一阶段的研究交付物

| 阶段 | 除代码/日志之外，必须回答 |
|---|---|
| 实现与 100-step smoke | 公式是否一致？三几何哪些通过？主要成本在哪里？哪些异常需要下一步诊断？ |
| 100M pilot | 稳定区间与预算是否合理？哪些机制假设值得做更长对照？尚不能断言什么？ |
| 1B 开发与调参 | 候选是否公平？收益是否只由 LR/角度造成？保留哪两个以内的结构候选，理由是什么？ |
| 3B 正式比较 | 各约束内配对效果如何？质量与时间是否一致？独立种子是否支持开发观察？ |
| 关键方法 6B | 结论是否依赖短预算？排名或收益是否改变？ |

建议逐阶段维护：

~~~text
research/
  hypotheses.md
  algorithm_decisions.md
  theory_alignment.md
  acceptance_targets.json
  development_summary.md
  protocol_lock.json
  claim_evidence.md
~~~

这些是目标设备需要生成和持续更新的研究输出，不是本包已经取得的结果。protocol_lock 至少锁定方法定义、候选列表、seed、数据切分、评价指标、最终 checkpoint 规则和预算；claim_evidence 每个论文主张都链接到具体 run 和允许的结论范围。

每轮汇报使用下面六项，便于作者决定算法方向：

1. 本轮在回答哪个问题；
2. 使用什么共同条件与唯一变化；
3. 观察到什么，并给出数据和 run；
4. 已排除哪些解释，还有哪些不确定；
5. 下一步具体改什么/不继续什么，以及理论身份；
6. 下一阶段需要多少 GPU-hours，当前总消耗多少。

## 10. 最终论文应能回答的 reviewer 问题

- 同约束下是否比该问题的强基线更好，还是只比了较弱实现？
- 优势来自切投影/方向几何，还是 LR、半径、数据或近似精度？
- 近似计算和约束误差是否改变了所声称的算法？
- 增益能否跨种子复现，花费多少额外时间和调参成本？
- 谱球面何时满足光滑前提，退出时如何处理？
- 为什么采用这些矩阵约束，固定架构比较能说明什么、不能说明什么？
- 有没有如实报告 MCSD/TP 重合、几何失效或负结果？

这些问题有可追溯答案，比增加网络大小、堆更多方法名称或只展示最低 loss 更有助于形成可信的实验部分。
