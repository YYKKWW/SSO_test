  approximately another 3B tokens to reach at least 6B in total. This is not

  `99ee6aaace88779d1ef099d36251b91101c1679b`.
- Keep the existing seven-component token proportions. New quotas are the
  six-billion-token component targets minus each component's original count.
  Full documents are retained, so the final count can slightly exceed 6B.
- The existing local OLMo-2 tokenizer is retained; each document has one

- For new documents, SHA256 of the full int32 token sequence is checked

  semantic/near-duplicate filter and does not retroactively clean the base.
- New source-file order uses seed 20261013 and is persisted before sampling.
  The initial 3B selection remains unchanged. Training sample shuffling is
  still the responsibility of the training data loader.

## Storage and recovery

Source text is streamed rather than stored as a large JSONL corpus. New
tokens are written in approximately 25M-token shards (about 100 MB each).
SQLite records deduplication keys, source-file/row cursors and committed
shards. Each shard is finalized and synced before its state is committed.
On interruption, committed shards are reused; only the uncommitted next
shard may be replaced. The input/source identity must match on resume.

There is one dataset writer, protected by an exclusive lock. Transient source
stream errors are retried at most four times after the first attempt, with
already yielded rows skipped on replay. A longer outage fails the job with
committed progress retained; no hidden automatic resubmission is configured.

The final merge copies the old 3B and the new shards into a new standalone
6B prefix. It checks counts, byte sizes and shard checksums, records final
hashes, and only then removes temporary new shards. Peak additional data
storage is roughly 12 GB of extension shards plus 24 GB for the final file,
plus index/database overhead. The old 3B is retained. Disk checks reserve
8 GiB and check merge capacity before starting it; disk insufficiency stops
the build without deleting the original datasets.
